SGLang推理优化-Scheduler 到 Forward 推理的 Batch 数据流

从 Scheduler 到 Forward 的 Batch 数据流

本文围绕 Scheduler 调度器到模型 forward 之间最关键的三个 Batch 数据结构展开：

●●●
1ScheduleBatch
2  -> ModelWorkerBatch
3  -> ForwardBatch

上一篇调度器ScheduleBatch重点解释 Scheduler 如何决定“下一轮跑 prefill 还是 decode”。本文继续往后走，解释这个决定出来的 ScheduleBatch 如何一步步变成模型真正执行时消费的 ForwardBatch然后模型开始使用input_ids开始做module forward一系列工作。

一句话理解

这三个对象不是重复封装，而是服务于三个不同层级：

●●●
1ScheduleBatch:
2Scheduler 视角。
3关心请求生命周期、调度状态、req 列表、prefix cache、KV cache 分配、采样参数。
4
5ModelWorkerBatch:
6Scheduler -> worker 的传输视角。
7把 ScheduleBatch 中 forward 需要的字段打包出来，减少 worker 侧直接依赖调度器内部状态。
8
9ForwardBatch:
10ModelRunner / attention backend / model.forward 的执行视角。
11  在 ModelWorkerBatch 基础上补齐 positions、attention metadata、KV pool、DP padding、LoRA、MROPE 等运行时信息。

核心数据流如下：

●●●
1┌─────────────────────────────────────────────┐

3│ 产物：ScheduleBatch                          │

5│ 包含：Req 列表、forward_mode、input_ids、     │

7└──────────────────────┬──────────────────────┘
8                       │

14│                                             │
15│ 包含：worker forward 必需字段，外加 logprob、 │

可以用一句话记：

●●●
1ScheduleBatch 管调度，
2ModelWorkerBatch 管跨层传递，
3ForwardBatch 管模型执行。

三个对象先拆开看
ScheduleBatch：调度器手里的 Batch

ScheduleBatch 是 Scheduler 的核心状态对象。它知道“这一组请求为什么能跑、应该怎么跑、跑完之后怎么回到调度生命周期”。

它的典型字段可以分成 5 类：

这些字段可以用下面这张表来直观理解：

字段
通俗含义
在 batch 构建中的作用
reqs
这一批真正包含哪些请求对象
Scheduler 后续要把 next token、finish 状态、logprob、统计信息写回到这些 Req 上
req_to_token_pool
请求行号到 KV slot 的映射表
记录每个请求每个 token 的 KV cache 位置，attention 读历史 KV 时会用到
token_to_kv_pool_allocator
KV cache 空位分配器
给本轮新 token 分配 out_cache_loc，也负责释放或回收 KV cache
tree_cache
prefix cache / radix cache
判断 prompt 前缀哪些 token 已经算过，决定 prefix_lens 和本轮还需要 prefill 的 token
forward_mode
这一轮 forward 类型
决定 batch 是 EXTEND、DECODE、MIXED 还是其他特殊模式
batch_is_full
running batch 是否已经满
如果已满，Scheduler 可以跳过部分新 prefill admission 检查
chunked_req
当前跨轮 chunked prefill 的请求
长 prompt 被切块时，用它记录那个还没 prefill 完的请求
is_prefill_only
这一批是否只做 prefill，不采样生成
embedding、打分、max_new_tokens=0 等场景会走这类逻辑
input_ids
本轮真的要送进模型的 token
prefill 时是未命中 cache 的 prompt token；decode 时通常是每个请求最新生成的一个 token
input_embeds
直接送进模型的 embedding
多模态或 embedding override 场景可能绕过普通 token embedding
req_pool_indices
每个请求在 req_to_token_pool 里的行号
attention 根据它找到每个请求对应的 KV slot 序列
seq_lens
 / seq_lens_cpu
每个请求当前完整序列长度
包括 prompt 和已生成 token；decode position 通常由它推出
orig_seq_lens
原始序列长度
某些长上下文或特殊模型需要知道未 chunk 前的真实长度
out_cache_loc
本轮新 KV 要写入的 KV slot
长度等于本轮实际 forward token 数；它是写地址，不是完整历史 KV 读取表
output_ids
本轮 decode 输入 token 的张量形式
decode batch 中通常来自每个请求上轮采样出的 token
prefix_lens
每个请求已经命中 cache 的前缀长度
prefill 时决定哪些 token 不需要重复计算
extend_lens
每个请求本轮要新算多少个 prompt token
和 prefix_lens 一起描述 EXTEND batch 的形状
extend_num_tokens
本轮所有 extend token 总数
等于拼平后的 extend input_ids 长度
extend_logprob_start_lens
prompt logprob 从哪里开始算
返回 input logprob 时用于跳过不需要回传的前缀
decoding_reqs
MIXED batch 中正在 decode 的请求
mixed chunked prefill 场景下，一个 batch 里可能同时有 decode 和 extend
sampling_info
采样参数的 batch 化结果
保存 temperature、top_p、top_k、grammar 等采样需要的信息
return_logprob
是否需要返回 logprob
决定 logits processor 是否额外保留 prompt/output logprob
top_logprobs_nums
每个请求要返回多少个 top logprobs
OpenAI API 风格的 top logprobs 返回需要它
token_ids_logprobs
指定 token 的 logprob 查询列表
用户只关心某些 token 的概率时使用
multimodal_inputs
图像、音频、视频等多模态输入
后续转换成 input_embeds、MROPE 位置或 encoder 信息
spec_info
speculative decoding 的运行信息
draft/verify 路径会用它改变输入、positions 和 logits 处理
global_num_tokens
DP attention 下全局 token 分布
多 DP rank 需要对齐 token 数、padding 和 MLP 同步
hicache_consumer_index
HiCache 数据加载同步索引
用于协调 CPU/GPU/远端 cache 的异步加载和消费

ScheduleBatch 的关键点是：它仍然保留 Req 对象列表。

●●●
1batch.reqs = [R1, R2, R3]

这意味着它不仅能跑 forward，还能在 forward 后把结果写回每个请求：

●●●
1req.output_ids
2req.finished_reason
3req.input_token_logprobs
4req.hidden_states
5req.time_stats

所以 ScheduleBatch 是“调度生命周期对象”，不是单纯的模型输入。

●●●

和 ScheduleBatch 相比，ModelWorkerBatch 有几个特点：

●●●
11. 它更接近 worker 输入，不负责调度 admission。
22. 它保留 reqs，主要是为了 grammar、rids、部分后处理和调试。
33. 它还没有 positions，也没有 attn_backend 的 runtime metadata。
44. 它不直接持有 token_to_kv_pool，KV pool 由 model_runner 注入到 ForwardBatch。

可以把它理解成：

●●●
1ScheduleBatch 的 forward 投影。
ForwardBatch：模型真正消费的 Batch

为什么不直接从 ScheduleBatch 到 ForwardBatch

看起来可以省掉 ModelWorkerBatch，但实际有几个原因需要中间层：

●●●
11. 隔离 Scheduler 内部状态
2   ScheduleBatch 带有 reqs、tree_cache、allocator、filter/merge 等调度逻辑。
3   model worker 不应该依赖这些调度细节。
4
52. 支持 overlap schedule
6   overlap 模式下 Scheduler 线程和 forward stream 并行。
7   ModelWorkerBatch 是一个更稳定的 forward 快照。
8
93. 支持不同 worker 类型
10   TP worker、speculative worker、embedding worker、MLX worker 都可以围绕 ModelWorkerBatch 建接口。
11
124. 运行时对象必须由 ModelRunner 注入
13   token_to_kv_pool、attn_backend、device-specific positions 不属于 Scheduler。
14   它们在 ForwardBatch.init_new 中由 model_runner 注入更合理。
常见容易绕的点
1. input_ids 在三层中是同一批 token，但含义取决于 forward_mode
●●●
1EXTEND:
2  input_ids 是未命中 prefix cache 的 prompt token 拼平。
3
4DECODE:
5  input_ids 是每个请求上一轮采样出的最后一个 token。
2. positions 不在 ScheduleBatch 中

Scheduler 不直接生成 positions。它只提供：

●●●
1seq_lens
2prefix_lens
3extend_lens
4extend_num_tokens

真正的 positions 在 ForwardBatch.init_new 中生成，因为它依赖 model runner 的后端、device 和特殊模型逻辑。

3. out_cache_loc 由 Scheduler 分配，但由 attention 执行使用
●●●
1ScheduleBatch.prepare_for_extend / prepare_for_decode:
2  分配 out_cache_loc。
3
4ForwardBatch:
5  携带 out_cache_loc。
6
7attention backend / attention layer:
8  根据 out_cache_loc 把新 KV 写入 token_to_kv_pool。
4. sampling_info 从 ScheduleBatch 一直传到 ForwardBatch

sampling_info 在 ScheduleBatch.prepare_for_extend 或 decode 生命周期中创建/维护，然后一路传到 ForwardBatch。采样时 ModelRunner.sample 会使用它：

●●●
1temperature
2top_p
3top_k
4min_p
5presence/frequency penalty
6grammar mask
7logprob 参数
5. ForwardBatch 是局部执行对象

ForwardBatch 通常只在一次 forward 中使用。forward 结束后，结果会通过 GenerationBatchResult 回到 Scheduler，再由 ScheduleBatch 和 Req 更新长期状态。

●●●
1ForwardBatch:
2  执行期临时对象。
3
4ScheduleBatch / Req:
5  调度和请求生命周期状态。
最后串起来

一次普通 generation 的主路径可以总结成：

●●●
1Req
2-> Scheduler admission
3-> ScheduleBatch.prepare_for_extend / prepare_for_decode
4-> ScheduleBatch.get_model_worker_batch
5-> TPWorker.forward_batch_generation
6-> ForwardBatch.init_new
7-> attention_backend.init_forward_metadata
8-> model.forward(input_ids, positions, forward_batch)
9-> embed_tokens(input_ids) / input_embeds
10-> hidden_states
11-> transformer layers(hidden_states, positions, forward_batch)
12-> logits processor
13-> sampler
14-> GenerationBatchResult
15-> Scheduler.process_batch_result
16  -> Req.output_ids / finished 状态更新

理解这条链路后，再看 DP attention、overlap schedule、speculative decoding、cuda graph、multimodal、LoRA 等分支，本质上都是在这三个 Batch 对象上增加字段、补 runtime metadata，或者改变它们的转换时机。

SGLang DP 并行推理优化

Native DP Single-Node

本文梳理 SGLang 内置 Native DP 在单机上的启动、rank 映射、ZMQ 请求分发和 NCCL/TP 集合通信逻辑。

这里讨论的是 python -m sglang.launch_server 的内置 DP，也就是 DataParallelController + launch_dp_schedulers 这条路径，不是 SGLang Model Gateway，也不是 DP attention。

示例配置：

●●●
1--nnodes 1
2--dp 2
3--tp 4

假设单机 8 张 GPU，总共启动 2 个 DP replica，每个 replica 使用 4 张 GPU 做 TP。

一句话理解

普通 Native DP 是“多个完整模型副本”。

在单机 8 卡 dp2 + tp4 下：

●●●
1DP0 replica:
2  使用 GPU 0,1,2,3
3  内部是一个 TP4 group
4  tp_rank = 0,1,2,3
5
6DP1 replica:
7  使用 GPU 4,5,6,7
8  内部是另一个 TP4 group
9  tp_rank = 0,1,2,3

注意：两个 DP replica 里的 tp_rank 都是 0..3。它们不是同一个 TP8 world，而是两个互相独立的 TP4 world。

这和 DP attention 很不一样：

●●●
1普通 Native DP:
2  dp2 + tp4 = 两套独立 TP4 模型副本，总共 8 卡。
3
4DP attention:
5  dp4 + tp16 = 一个 TP16 world 内切出 4 个 attention DP group。

launch_tensor_parallel_group 做了什么

普通 DP 下，launch_tensor_parallel_group 是被每个 DP replica 分别调用的：

●●●
1DP0 thread -> launch_tensor_parallel_group(..., base_gpu_id=0, dp_rank=0)

第 1 步：算当前 node 的 TP rank 范围

●●●

2tp_size_per_node = server_args.tp_size // nnodes_per_tp_group

所以每个 DP replica 都会启动：

●●●

注意：DP0 和 DP1 的 tp_rank 都是 0..3。它们属于不同进程组，所以 rank 编号可以重复。

第 2 步：普通 DP 不会从 tp_rank 反推 dp_rank

DP attention 模式下，dp_rank 是由 tp_rank 反推的。

普通 DP 模式下不是这样。dp_rank 来自外层 launch_dp_schedulers：

●●●
1DP0 thread 传入 dp_rank=0
2DP1 thread 传入 dp_rank=1

●●●

也就是说，一个 DP replica 内的所有 TP rank 共用同一个 rank_port_args，它们使用同一个 scheduler input IPC 和同一个 NCCL port。

NCCL / TP 集合通信逻辑

普通 Native DP 下，两个 DP replica 没有跨 DP 的 NCCL collective。

每个 DP replica 内部单独初始化 TP group：

●●●
1DP0 NCCL world:
2  GPU 0,1,2,3
3  tp_rank 0,1,2,3
4
5DP1 NCCL world:
6  GPU 4,5,6,7
7  tp_rank 0,1,2,3

每个 replica 内部的模型计算和集合通信就是普通 TP：

●●●
1tensor parallel all-reduce
2all-gather
3reduce-scatter
4attention TP broadcast
5logits / sampler 相关同步

但这些通信只发生在当前 DP replica 的 TP4 world 内。

对比 DP attention：

●●●
1普通 DP:
2  DP0 和 DP1 是两个独立模型副本。
3  DP0 的 TP collective 不需要 DP1 参与。
4  DP1 没请求时，DP1 可以 idle，不会影响 DP0 forward。
5
6DP attention:
7  所有 rank 在同一个 TP world 内。
8  attention 可分 DP group，但 MLP/MoE 前后需要同步 token 元信息。
9  idle DP 也可能要进入 collective，避免其他 rank hang。

因此普通 DP 没有 prepare_mlp_sync_batch_raw 这套跨 DP token 元信息同步，也没有 DP attention 里的 global_num_tokens、DP padding mode、DP hidden states gather/scatter 逻辑。

KV cache 和模型权重的含义

普通 Native DP 是完整模型副本。

在 dp2 + tp4 下：

●●●
1DP0:
2  拥有一套模型权重分片。
3  TP4 内每张 GPU 持有当前 TP rank 对应的权重 shard。
4  DP0 管自己的请求和 KV cache。
5
6DP1:
7  拥有另一套模型权重分片。
8  TP4 内每张 GPU 持有当前 TP rank 对应的权重 shard。
9  DP1 管自己的请求和 KV cache。

DP0 和 DP1 之间不共享请求状态，也不共享 KV cache。

这也是普通 DP 的核心取舍：

●●●
1优点:
2  简单，隔离性强。
3  一个 DP replica 忙，不要求其他 DP replica 同步参与。
4  适合吞吐扩展。
5
6代价:
7  模型权重和 KV cache 按 DP replica 复制。
8  同样 8 张卡，dp2+tp4 每个请求最多只用其中一个 TP4 replica。

SGLang Model Gateway 如何实现类似 DP 扩展

SGLang Model Gateway，简称 SMG，提供的是另一种更现代的 DP 扩展方式。

Native DP 是：

●●●
1一个 sglang.launch_server 进程树
2  -> 内部 DataParallelController
3  -> 内部启动多个 DP replica
4  -> Controller 用 ZMQ 把请求分给 replica

SMG 是：

●●●
1一个 Rust gateway / router
2  -> 管理多个独立 SGLang worker server
3  -> 通过 HTTP 或 gRPC 把请求路由到某个 worker

也就是说，SMG 不把多个 DP replica 塞进同一个 SGLang server 的内部进程结构里，而是把它们提升为多个独立 worker 实例，再由 gateway 统一做路由。

Co-launch 模式

SMG 的 Python launcher 支持一条命令同时启动 router 和多个 worker：

●●●
1python -m sglang_router.launch_server \
2  --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
3  --dp-size 2 \
4  --tp-size 4 \
5  --host 0.0.0.0 \
6  --port 30000

入口在：

●●●
1sgl-model-gateway/bindings/python/src/sglang_router/launch_server.py

核心逻辑是：

●●●
1worker_ports = find_available_ports(
2    args.router_dp_worker_base_port, server_args.dp_size
3)
4
5for i, worker_port in enumerate(worker_ports):
6    proc = launch_server_process(server_args, worker_port, i)
7    server_processes.append(proc)
8
9protocol = "grpc" if server_args.grpc_mode else "http"
10router_args.worker_urls = [
11    f"{protocol}://{server_args.host}:{port}" for port in worker_ports
12]
13
14launch_router(router_args)

每个 worker 启动时会改写参数：

●●●
1server_args.port = worker_port
2server_args.base_gpu_id = dp_id * server_args.tp_size
3server_args.dp_size = 1

所以单机 8 卡 dp2 + tp4 在 SMG co-launch 下可以理解为：

●●●
1Router:
2对外监听 port 30000
3
4Worker 0:
5独立 sglang server
6port = 31000 附近的某个可用端口
7base_gpu_id = 0
8dp_size = 1
9tp_size = 4
10使用 GPU 0,1,2,3
11
12Worker 1:
13独立 sglang server
14port = 31000 附近的另一个可用端口
15base_gpu_id = 4
16dp_size = 1
17tp_size = 4
18  使用 GPU 4,5,6,7

注意这里 worker 内部已经不是 Native DP 了：

●●●
1每个 worker 自己是普通 tp4 server；
2DP 这个概念由 router 层实现；
3worker 之间通过 HTTP/gRPC 隔离。
Separate launch 模式

也可以先独立启动 worker，再让 router 连接它们：

●●●
1# Worker 0
2python -m sglang.launch_server \
3--model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
4--tp-size 4 \
5--base-gpu-id 0 \
6--port 8000
7
8# Worker 1
9python -m sglang.launch_server \
10--model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
11--tp-size 4 \
12--base-gpu-id 4 \
13--port 8001
14
15# Router
16python -m sglang_router.launch_router \
17--worker-urls http://127.0.0.1:8000 http://127.0.0.1:8001 \
18--policy cache_aware \
19--host 0.0.0.0 \
20--port 30000

这时请求路径是：

●●●
1Client
2|
3| HTTP / OpenAI-compatible API
4v
5SMG Router
6|
7| policy select worker
8|
9+--> Worker 0, TP4, GPU 0..3
10  +--> Worker 1, TP4, GPU 4..7

这和 Native DP 的形态很像，都是“两个 TP4 副本做吞吐扩展”。区别是 Native DP 的 router 是 SGLang server 内部的 DataParallelController，SMG 的 router 是独立 Rust gateway。

SMG 的 worker registry 和 policy

SMG 会把 worker 注册到 worker registry：

●●●
1sgl-model-gateway/src/core/worker_registry.rs

这个 registry 按 model 维护 worker 索引，并支持：

●●●
1按 model 查 worker
2按健康状态过滤 worker
3按 worker type 区分 regular / prefill / decode
4为 consistent hashing 维护 hash ring

路由策略由 policy factory 创建：

●●●
1sgl-model-gateway/src/policies/factory.rs

支持的策略包括：

●●●
1random
2round_robin
3power_of_two
4cache_aware
5bucket
6manual
7consistent_hashing
8prefix_hash

其中 cache_aware 是 SMG 相比 Native DP 的一个重要能力。它维护近似 prefix tree，根据请求前缀和已有 cache affinity 选择 worker：

●●●
1如果系统负载均衡:
2  尽量把相似 prefix 的请求路由到可能已经有 prefix cache 的 worker。
3
4如果系统负载不均衡:
5  切到负载均衡逻辑，把请求发给更空闲的 worker。

这比 Native DP 的 round_robin / total_requests / total_tokens 更适合真实在线流量，因为 LLM serving 的性能经常受 prefix cache 命中率影响。

DP-aware worker discovery

SMG 也有 DP-aware discovery：

●●●
1sgl-model-gateway/src/core/steps/worker/local/discover_dp.rs

核心逻辑：

●●●
1let info = get_server_info(url, api_key).await?;
2let dp_size = info.dp_size.ok_or_else(...)?;
3let model_id = info.model_id
4    .or(info.served_model_name)
5    .or_else(...)

它会从 worker 的 server info 里发现：

●●●
1dp_size
2model_id
3served_model_name
4model_path

这让 gateway 可以在更复杂部署中理解 worker 的 DP 信息，而不是只把 worker 当成一个普通 URL。

为什么 SMG 更好

Native DP 的优点是实现简单：一个 SGLang server 内部起多个 replica，内部 ZMQ 分发请求。但它的问题也来自这个设计。

SMG 更适合生产的原因主要有这些。

第一，路由策略更强。

Native DP 主要是：

●●●
1round_robin
2total_requests
3total_tokens
4follow_bootstrap_room

SMG 支持：

●●●
1cache_aware
2power_of_two
3prefix_hash
4manual
5consistent_hashing
6bucket
7round_robin
8random

其中 cache-aware / prefix-hash 对 prefix cache 友好，可以减少重复 prefill，提高缓存命中。

第二，worker 是独立 server，隔离性更好。

Native DP：

●●●
1一个父进程树内部管理多个 DP replica。
2某个 replica 的异常更容易影响整个 server 生命周期。
3升级、替换、下线粒度较粗。

SMG：

●●●
1每个 worker 是独立 SGLang server。
2router 只通过 HTTP/gRPC 和 worker 通信。
3worker 可以独立重启、扩缩容、替换。

第三，故障处理更完善。

SMG 有 circuit breaker 和 retry：

●●●
1sgl-model-gateway/src/core/circuit_breaker.rs
2sgl-model-gateway/src/core/retry.rs

它可以对失败 worker 做熔断、半开探测、重试和 backoff。Native DP 的 DataParallelController 更偏本地进程内分发，不是完整的生产 gateway 故障治理系统。

第四，观测和运维能力更强。

SMG 是独立 gateway，天然适合做：

●●●
1worker selection metrics
2router latency metrics
3error metrics
4worker health check
5multi-worker registry
6multi-model routing
7Kubernetes service discovery
8mesh / multi-router 扩展

Native DP 更像 SGLang server 内部的一个简单 DP controller。

第五，部署形态更灵活。

Native DP 受限于单个 SGLang launch 进程树，并且本地代码里明确限制：

●●●
1assert not (
2    self.dp_size > 1 and self.nnodes != 1 and not self.enable_dp_attention
3), "multi-node data parallel is not supported unless dp attention!"

也就是说，普通 Native DP 不支持多机 DP。

SMG 可以连接任意多个 worker URL：

●●●
1同机多个 worker
2多机多个 worker
3Kubernetes 多 pod
4HTTP worker
5gRPC worker
6PD disaggregation worker

因此它更适合作为真正的生产 DP routing 层。

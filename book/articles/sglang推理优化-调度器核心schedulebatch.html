SGLang推理优化-调度器核心ScheduleBatch

本文围绕 Scheduler 调度器里最核心的 Batch 构建逻辑展开：

●●● 
1get_next_batch_to_run
2  -> get_new_batch_prefill
3  -> update_running_batch

这条链路决定了下一次 forward 到底跑什么，是新的 prefill，还是已有请求的 decode。Batch 构建逻辑比较绕，建议先用下面的模拟请求把状态流转看懂，再回到代码里逐行阅读。


一句话理解

Scheduler 每一轮调度，本质是在回答一个问题：
●●● 
1下一次 model forward 应该跑哪个 Batch？

这个问题不能只看 waiting_queue，也不能只看 running_batch，而是要同时处理 4 类状态：

●●● 
1last_batch:
2上一轮刚 forward 完的 batch。
3它可能是 EXTEND，也可能是 DECODE。
4只有 EXTEND 才可能在本轮开头并入 running_batch。
5
6waiting_queue:
7等待第一次或下一段 prefill 的请求。
8
9running_batch:
10已经完成 prefill、后续可以 decode 的请求集合。
11
12chunked_req:
13  长 prompt 被切块后，尚未完成全部 prefill 的请求。

这里最重要的优先级是：

●●● 
1last_batch 如果是 EXTEND，合入 running_batch 发生在本轮最开始。
2新 prefill batch 的优先级高于 running decode。
3只有 get_new_batch_prefill 返回 None，才会进入 update_running_batch。

换句话说：

●●● 
1waiting_queue / chunked_req 能组出 EXTEND:
2  本轮跑 prefill。
3
4组不出 EXTEND，但 running_batch 里还有活请求:
5  本轮跑 decode。
6
7两者都没有:
8  本轮空转。

这个优先级解释了一个常见现象：即使 running_batch 里已经有很多请求在等 decode，只要 Scheduler 还能安全接入新的 prefill，它仍然会先返回 EXTEND batch。

代码主干先拆开看

这部分代码最绕的原因是：一个函数里同时处理“调度决策”和“状态迁移”。建议先把三个函数的职责边界分清楚。
●●● 
1get_next_batch_to_run:
2调度总控。
3负责判断上轮 batch 是否需要合入 running_batch，并决定本轮返回 EXTEND / DECODE / None。
4
5get_new_batch_prefill:
6prefill admission。
7负责从 waiting_queue / chunked_req 中挑出可以 prefill 的请求，并构造成 EXTEND batch。
8
9update_running_batch:
10decode admission。
11  负责过滤 running_batch、检查 decode KV 空间、必要时 retract，然后构造成 DECODE batch。
get_next_batch_to_run 的关键分段

可以把 get_next_batch_to_run 看成 5 个连续阶段。
●●● 
1阶段 1：处理不能继续等待或运行的请求
2
3_abort_on_waiting_timeout()
4_abort_on_running_timeout()
5DLLM / staging / chunked_req 特殊处理

这一段的重点不是构建 batch，而是保证后面的队列状态是干净的。已经超时或被 abort 的请求，不能继续参与 admission。

●●● 
1阶段 2：处理上轮 batch
2
3if last_batch.forward_mode.is_extend():
4    last_batch.filter_batch(chunked_req_to_exclude=...)
5    running_batch.merge_batch(last_batch)

last_batch 是 event loop 每轮末尾直接赋值的：

●●● 
1batch = get_next_batch_to_run()
2run_batch(batch)
3process_batch_result(batch, result)
4self.last_batch = batch

所以它可能是：

●●● 
1EXTEND:
2  上轮跑的是 prefill。
3  本轮开头需要考虑是否把它合入 running_batch。
4
5DECODE:
6  上轮跑的是 decode。
7  它本来就是 running_batch 的推进结果，不需要再次 merge。
8
9None:
10  上轮没有 batch。

因此代码只处理：

●●● 
1self.last_batch.forward_mode.is_extend()

这是 prefill 到 decode 生命周期的入口。上一轮返回的 EXTEND batch 经过 forward 和采样后，会在本轮开头尝试合入 running_batch。

这一段有两个关键细节：

●●● 
1filter_batch:
2  去掉已经 generation finished 的请求。
3  通过 chunked_req_to_exclude 排除还没有完成全部 prefill 的 chunked_req。
4
5merge_batch:
6  合并 reqs / req_pool_indices / seq_lens / sampling_info 等 batch 级状态。
7  不是简单地 list extend。

这里“可以合入 running_batch”的含义是：

●●● 
1普通非 chunked prefill:
2  prefill forward 完成后，只要请求没有 generation finished，就可以合入 running_batch。
3
4chunked prefill:
5  中间 chunk 不能合入 running_batch。
6  只有最后一个 chunk 完成后，self.chunked_req 不再指向它，它才会通过 filter_batch 并被 merge。
7
8prefill-only / 已经生成结束的请求:
9  会被 filter_batch 过滤掉，不进入 decode。
●●● 
1阶段 3：优先尝试新 prefill
2
3new_batch = get_new_batch_prefill()
4
5if new_batch is not None:
6    ret = new_batch

这就是 prefill 优先级的来源。只要 get_new_batch_prefill 能组出一个 batch，本轮就不会走普通 decode。

●●● 
1阶段 4：没有 prefill 时，才推进 running decode
2
3if new_batch is None:
4    if not running_batch.is_empty() and not running_batch.is_prefill_only:
5        running_batch = update_running_batch(running_batch)
6        ret = running_batch

这里的 update_running_batch 不只是“把 forward_mode 改成 DECODE”，它会先过滤 finished 请求、检查内存、必要时 retract。

●●● 
1阶段 5：返回前做 DP attention / ngram / schedule time 处理
2
3maybe_prepare_mlp_sync_batch(ret)
4_maybe_prepare_ngram_embedding(ret)
5set_schedule_time_batch(ret)

所以主干决策是前 4 段，最后一段是返回 batch 前的补充处理。

get_new_batch_prefill 的关键分段

get_new_batch_prefill 的核心是 admission：决定哪些请求可以进入本轮 EXTEND batch。

它不是按条数拿请求，而是按资源预算逐个尝试：
●●● 
1waiting_queue
2  -> policy.calc_priority
3  -> Req.init_next_round_input
4  -> PrefillAdder.add_one_req
5  -> can_run_list
6  -> ScheduleBatch.prepare_for_extend

关键代码可以分成 6 段。

●●● 
1阶段 1：快速失败
2
3if running_batch.batch_is_full and chunked_req is None:
4    return None
5
6if waiting_queue is empty and chunked_req is None:
7    return None
8
9if get_num_allocatable_reqs(running_bs) <= 0 and chunked_req is None:
10    running_batch.batch_is_full = True
11    return None

这里检查的是“有没有必要尝试 prefill”。如果 running batch 已满、没有等待请求、请求池没有槽位，就直接返回 None，让外层去尝试 decode。

●●● 
1阶段 2：给 waiting_queue 排优先级
2
3policy.calc_priority(waiting_queue, running_batch)

这一步会改变 waiting_queue 的调度顺序。后续 for req in waiting_queue 不是原始到达顺序，而是策略处理后的顺序。

●●● 
1阶段 3：创建 PrefillAdder
2
3adder = PrefillAdder(
4    page_size,
5    tree_cache,
6    token_to_kv_pool_allocator,
7    running_batch,
8    new_token_ratio,
9    max_prefill_tokens,
10    chunked_prefill_size,
11    ...
12)

这里 PrefillAdder.__init__ 的参数名是 rem_input_tokens，但调用方传进去的是：

●●● 
1self.max_prefill_tokens

对应关系是：

●●● 
1Scheduler._get_new_batch_prefill_raw:
2  PrefillAdder(..., self.max_prefill_tokens, chunked_prefill_size, ...)
3
4PrefillAdder.__init__:
5  def __init__(..., rem_input_tokens, rem_chunk_tokens, num_mixed_decode_tokens=0, ...):
6      self.rem_input_tokens = rem_input_tokens - num_mixed_decode_tokens

所以：

●●● 
1rem_input_tokens 的初始值
2  = Scheduler.max_prefill_tokens
3  - mixed chunked prefill 中预留给 decode 的 token 数

Scheduler.max_prefill_tokens 又来自 model worker 初始化阶段：

●●● 
1self.tp_worker.get_worker_info()
2  -> self.max_prefill_tokens

从配置角度看，它最终受 ServerArgs.max_prefill_tokens、模型 worker 可用 KV/显存预算、后端实现等共同影响。对调度器这段代码而言，它就是“本轮 prefill 最多允许消耗多少 input token”的预算上限。

PrefillAdder 的作用是维护本轮 prefill 的动态预算：

●●● 
1can_run_list:
2已经决定本轮可以跑的请求。
3
4rem_input_tokens:
5本轮 prefill input token 预算还剩多少。
6初始来自 self.max_prefill_tokens，后续每加入一个请求都会扣减。
7
8rem_total_tokens:
9KV cache 可用量扣掉 running_batch 未来 decode 预留后的余量。
10
11rem_chunk_tokens:
12chunked prefill 本轮还能吃多少 token。
13
14preempt_list:
15  priority preemption 下被撤回的 running 请求。
●●● 
1阶段 4：优先处理未完成的 chunked_req
2
3if chunked_req is not None:
4    chunked_req.init_next_round_input()
5    chunked_req = adder.add_chunked_req(chunked_req)

这个分支很关键。长 prompt 的中间 chunk 已经占用了部分状态，如果不优先继续调度，会造成资源和状态难以收敛。因此 chunked_req 的优先级高于普通 waiting_queue。

●●● 
1阶段 5：逐个尝试 waiting_queue 里的请求
2
3for req in waiting_queue:
4    if running_batch.batch_is_full:
5        break or preempt_to_schedule(req)
6
7    req.init_next_round_input(tree_cache)
8    res = adder.add_one_req(req, ...)
9
10    if res != CONTINUE:
11        break

这一段是最关键的地方。

req.init_next_round_input(tree_cache) 会先做：

●●● 
1fill_ids = origin_input_ids + output_ids
2prefix_indices = tree_cache.match_prefix(...)
3extend_input_len = len(fill_ids) - len(prefix_indices)

也就是说，进入 add_one_req 前，请求已经知道：

●●● 
1完整序列多长
2命中多少 KV cache
3本轮真正还要计算多少 token

adder.add_one_req 再判断：

●●● 
1extend_input_len + max_new_tokens + page_size 是否超过 rem_total_tokens
2实际 input tokens 是否超过 rem_input_tokens
3chunked_prefill_size 是否需要截断
4prefix cache host hit 是否需要 load back
5是否需要 lock tree cache node

如果允许加入：

●●● 
1adder.can_run_list.append(req)
2adder._update_prefill_budget(...)

_update_prefill_budget 会扣减：

●●● 
1rem_input_tokens -= ceil_paged_tokens(extend_input_len)
2rem_total_token_offset += extend_input_len + max_new_tokens + page_size
3rem_chunk_tokens -= extend_input_len       # 如果开启 chunked prefill

如果不允许：

●●● 
1返回 NO_TOKEN / OTHER
2外层 break，本轮 prefill batch 到此为止
●●● 
1阶段 6：把 can_run_list 变成 EXTEND batch
2
3waiting_queue -= can_run_list
4
5new_batch = ScheduleBatch.init_new(can_run_list, ...)
6new_batch.prepare_for_extend()
7return new_batch

ScheduleBatch.init_new 只创建 batch 对象；prepare_for_extend 才真正把 Req 转成 forward 所需张量。

prepare_for_extend 的关键产物

prepare_for_extend 的核心输入是每个请求的：
●●● 
1fill_ids
2prefix_indices
3extend_input_len

它构造出的关键字段是：

●●● 
1input_ids:
2每个请求未命中 prefix cache 的 token，全部拼平成一个 tensor。
3
4seq_lens:
5每个请求 forward 后的完整长度。
6
7prefix_lens:
8每个请求命中的 prefix 长度。
9
10extend_lens:
11每个请求本轮实际 extend 的 token 数。
12
13out_cache_loc:
14每个 extend token 对应的 KV cache 写入地址。
15
16req_pool_indices:
17每个请求在 req_to_token_pool 中的位置。
18
19sampling_info:
20  采样参数按 batch 聚合后的结构。

这一步还有一个容易忽略的副作用：它会更新 Req 自身的内存状态。

●●● 
1req.req_pool_idx = req_pool_indices[i]
2req.kv_committed_len = seq_len
3req.kv_allocated_len = seq_len
4req.extend_batch_idx += 1
5req.cached_tokens / already_computed 更新

所以 prepare_for_extend 不是纯粹构造 tensor，它也把请求正式推进到了“已经为 prefill 分配资源”的状态。

update_running_batch 的关键分段

update_running_batch 的任务是把 running_batch 变成下一轮 decode batch。

主干可以拆成 4 段：
●●● 
1阶段 1：过滤已经完成的请求
2
3initial_bs = batch.batch_size()
4batch.filter_batch(v1_spec_info_filtered=True)
5
6if batch.is_empty():
7    batch.batch_is_full = False
8    return batch

这里会把已经 finished 的请求从 running_batch 中移除，并同步过滤 req_pool_indices、seq_lens、sampling_info 等 batch 字段。

●●● 
1阶段 2：检查下一步 decode 内存
2
3if not batch.check_decode_mem():
4    retracted_reqs, new_token_ratio, reqs_to_abort = batch.retract_decode(...)

check_decode_mem 会估算下一次 decode 需要多少 KV cache：

●●● 
1普通 decode:
2  每个请求通常需要 1 个新 token 的 KV 空间。
3
4page allocator:
5  如果跨 page 边界，需要按 page_size 申请。
6
7speculative decoding:
8  可能一次预留多个 draft / verify token 的空间。

如果空间不够，就进入 retract。

●●● 
1阶段 3：retract 后把请求放回 waiting_queue
2
3for req in retracted_reqs:
4    self._add_request_to_queue(req, is_retracted=True)

retract 会释放这些请求占用的 KV cache，但不会丢失请求进度。请求带着已有 output_ids 回到 waiting_queue，后续会再次通过 init_next_round_input 做 prefix match。

●●● 
1阶段 4：构建 DECODE batch
2
3batch.prepare_for_decode()
4return batch

prepare_for_decode 做的事情和 prepare_for_extend 完全不同：

●●● 
1input_ids:
2  不再是 prompt token，而是每个请求上一步采样出的最后一个 token。
3
4out_cache_loc:
5  为每个请求本轮 decode 的新 token 分配 KV 写入位置。
6
7seq_lens:
8  每个请求长度 +1。
9
10forward_mode:
11  改成 DECODE。

所以 update_running_batch 的本质是：

●●● 
1running_batch
2  -> filter finished
3  -> ensure decode memory
4  -> retract if needed
5  -> prepare_for_decode
6  -> DECODE batch
先看三个重要对象
Req 是请求的状态机

Req 不是只保存输入 prompt，它会在调度和 forward 过程中持续变化。

一个生成请求可以简化成：
●●● 
1Req(
2  rid="R1",
3  origin_input_ids=[11, 12, 13, 14],
4  output_ids=[],
5  prefix_indices=[],
6  fill_ids=[],
7  extend_input_len=0,
8  req_pool_idx=None,
9)

关键字段可以这样理解：

字段
含义
origin_input_ids
用户 prompt 的 token ids
output_ids
已经采样出来的输出 token ids
fill_ids
当前需要考虑的完整序列，通常是 origin_input_ids + output_ids
prefix_indices
prefix cache 命中的 KV 位置

ScheduleBatch 是 forward 前的批处理数据

ScheduleBatch 是 Scheduler 传给 model worker 的 batch 状态。

它既保存请求列表：
●●● 
1batch.reqs = [R1, R2, R3]

也保存 forward 需要的张量：

●●● 
1batch.input_ids
2batch.req_pool_indices
3batch.seq_lens
4batch.out_cache_loc
5batch.sampling_info

最关键的是 forward_mode：

●●● 
1EXTEND:
2  prefill，新请求或 chunked prefill 的一段 prompt。
3
4DECODE:
5  decode，running_batch 中每个请求继续生成一个 token。
6
7MIXED:
8  mixed chunked prefill，把新 prefill 和已有 decode 混在同一次 forward。
9
10IDLE:
11  DP attention 等场景下用于同步的空 batch。
PrefillAdder 是 admission controller

PrefillAdder 决定 waiting_queue 里的请求哪些能进入新的 prefill batch。

它同时考虑：
●●● 
1请求池槽位是否足够
2KV cache token 预算是否足够
3max_prefill_tokens 是否足够
4chunked_prefill_size 是否足够
5prefix cache 命中后实际需要算多少 token
6running_batch 未来 decode 还要预留多少 token

为什么 prefill 后要下一轮才合入 running_batch

因为 get_next_batch_to_run 返回 batch 后，还要经过：
●●● 
1run_batch
2  -> model forward
3  -> sampling
4  -> process_batch_result
5  -> 更新 req.output_ids / finished 状态

只有 forward 结束后，Scheduler 才知道：

●●● 
1这个请求是否 finished
2采样出了哪个 token
3output_ids 是否更新
4logprob / hidden states 等结果如何处理

所以 prefill batch 不能在构建出来时立刻进入 decode。它必须先作为 last_batch 经过一次 forward 结果处理，然后在下一轮调度开头经过 filter_batch。

合入规则可以简化成：

●●● 
1last_batch 不是 EXTEND:
2不处理。
3例如上一轮是 DECODE，它已经属于 running_batch 的生命周期。
4
5last_batch 是 EXTEND，且请求已经 generation finished:
6filter_batch 过滤掉，不进入 running_batch。
7
8last_batch 是 EXTEND，但请求仍是未完成的 chunked_req:
9通过 chunked_req_to_exclude 排除，不进入 running_batch。
10
11last_batch 是 EXTEND，且请求 prefill 已完整完成、还需要继续生成:
12  合入 running_batch，后续参与 decode。
update_running_batch 中的 retract 是什么

decode 阶段每轮都要给每个 running request 新增 KV cache。

如果当前 running_batch 太大，下一步 decode 的 KV cache 不够，update_running_batch 会触发：
●●● 
1batch.retract_decode(...)

可以把 retract 理解成：

●●● 
1为了避免 decode OOM，临时撤回一部分 running 请求。
2撤回请求会释放 KV cache，并重新放回 waiting_queue。
3后续它们会以带 output_ids 的状态重新 prefill / prefix match。

简化例子：

●●● 
1running_batch = [R1,R2,R3,R4]
2下一步 decode 需要 4 个 KV slot
3但当前只能再分配 2 个 KV slot

可能发生：

●●● 
1保留: [R1,R2]
2撤回: [R3,R4]
3
4running_batch = [R1,R2]
5waiting_queue = [R3,R4]

撤回的请求不是丢掉，而是：

●●● 
1R3.origin_input_ids 不变
2R3.output_ids 保留已经生成的 token
3R3.is_retracted = True
4R3 后续重新进入 waiting_queue

下一次 init_next_round_input 时：

●●● 
1fill_ids = origin_input_ids + output_ids

所以它会尝试从 prefix cache 找回已经算过的 KV，只补算缺失部分。

常见容易绕的点
1. running_batch 不等于正在 forward 的 batch

running_batch 指的是“已经进入 decode 生命周期的请求集合”。

当前返回给 forward 的 batch 可能是：
●●● 
1EXTEND new_batch
2DECODE running_batch
3MIXED new_batch + running_batch
2. EXTEND last_batch 是 prefill 到 decode 的桥

last_batch 不一定是 prefill batch。event loop 每轮都会执行 self.last_batch = batch，所以上一轮返回 DECODE 时，last_batch 也是 DECODE。

只有当 last_batch.forward_mode.is_extend() 为 True 时，它才承担 prefill 到 decode 的桥接作用。下一轮调度开头会先 filter_batch，排除已经 generation finished 的请求和未完成的 chunked prefill，再把剩下的请求合入 running_batch。
3. input_ids 在 EXTEND 和 DECODE 中含义完全不同
●●● 
1EXTEND input_ids:
2  prompt 中没有命中 prefix cache 的 token。
3
4DECODE input_ids:
5  每个请求上一步采样出的最后一个 token。
4. prefix cache 命中会改变 admission 结果

两个 prompt 一样长的请求，命中多的请求 extend_input_len 更小，更容易被加入 prefill batch。
5. batch_is_full 是优化标记，不是绝对状态

running_batch.batch_is_full 用来减少无意义的 prefill 尝试。某些场景会重置它，比如：
●●● 
1有请求完成并被 filter 掉
2开启 priority preemption
3hybrid SWA
4retract 后 running batch 变小
6. 被 retract 的请求会回 waiting_queue

retract 不是失败，也不是丢请求，而是为了释放 decode KV cache。请求保留 output_ids，后面再通过 prefix cache 恢复。
最后用一句话串起来

ScheduleBatch 构建的核心可以这样记：
●●● 
1waiting_queue 里的 Req
2  -> init_next_round_input 做 prefix match
3  -> PrefillAdder 判断预算
4  -> ScheduleBatch.prepare_for_extend 变成 EXTEND forward 数据
5  -> forward 后作为 last_batch
6  -> 下一轮合入 running_batch
7  -> update_running_batch + prepare_for_decode 变成 DECODE forward 数据

理解了这个状态流转，再去看 DP attention、chunked prefill、overlap、speculative decoding、disaggregation 等分支，会容易很多。
